# issue-to-pr-flow — 利用ガイド

[English](guide.md)

このガイドは、フローを日々**使う**人のためのものです。Issue を書く、AI の投稿を読む、止まったときにどうするか決める、
作られた PR をレビューする――そのために必要なことだけをまとめています。スクリプトの仕組みを知る必要はありません。
導入方法や設計の背景は [setup.md](setup.md)（英語）にあります。Claude Code などのエージェントに導入させる場合は [setup-with-agent.md](setup-with-agent.md)（英語。エージェントが読むための手順書で、やりとりは日本語でできます）に従うよう指示してください。

---

## 1. 1 分でわかる全体像

あなたが GitHub Issue を書くと、フローが Claude Code を無人で動かして Pull Request まで仕上げます。

```
Issue を書く
   │
   ▼
make spec ISSUE=n    AI が Issue とコードを読み、次のどちらかを投稿する
                     ・質問
                     ・受け入れ条件（AC-1, AC-2, …）付きの指示書
   │
   ▼
人が読む             ← PR までの唯一のチェックポイント
   │
   ▼
make impl ISSUE=n    計画 → 計画の判定 → 実装 → 結果の判定 → 修正 → コミット → PR → コードレビュー
   │
   ▼
人が PR をレビューし、マージするか決める
```

覚えておくことは 3 つです。

- **人が確認するのは作業が始まる前の 1 回だけ。** 指示書を受け入れたら、PR ができるまで人を待つ場面はありません
- **「完了」とは「受け入れ条件がすべて満たされた」こと。** AI は自分の成果を `AC-1`、`AC-2`… だけに照らして判定し、好みでは判定しません。
  条件に書かれていないことはチェックされません。だからこそ指示書が一番大事です
- **終わらせられないときは、推測で進めずに止まって知らせます。** 止まるのは正常な動作で、何も失われません

AI がしたことはすべて Issue にコメントとして投稿されるので、経緯は Issue を読めば全部わかります。

## 2. 人がやること（手順）

### 手順 1: Issue を書く

**何をしたいか**と**なぜか**を書きます。どうやるかは書かなくて構いません。それは AI が計画します。

| 良い例 | あまり良くない例 |
|---|---|
| 「レポートの書き出しが既存ファイルを確認なしで上書きする。2 回データを失った。ファイルがあるときは拒否してほしい。」 | 「書き出しを直す。」 |
| 1 つの Issue に目的は 1 つ | 「書き出しを直して、ついでに設定画面の名前も変える」（目的が 2 つ → Issue を 2 つに） |

Issue の大きさは、触るファイルの数ではなく**目的の数**で測ります。
細部がわからなくても、わかっていることを書けば十分です。AI が質問してきます。

### 手順 2: `make spec` を実行する

```sh
cd ai-flow          # リポジトリ内のフローのディレクトリ
make spec ISSUE=12
```

数分かかります。終わると、Issue に次のどちらかのコメントが付きます（通知を設定していれば通知も届きます）。

**質問**（`QUESTION`）― まだ決まっていない重要な点があります。各質問には推奨案とその理由が付いています。
Issue にコメントで回答し（「推奨どおりで」で構いません）、もう一度 `make spec ISSUE=12` を実行します。

**指示書**（`INSTRUCTION`）― AI が理解した作業内容です。手順 3 へ。

### 手順 3: 指示書を読む（チェックポイント）

フロー全体で一番大事な 5 分間です。この後のすべてが、この文書に照らして判定されます。

指示書の中身と見るポイント:

| セクション | 確認すること |
|---|---|
| 背景と目的 | **なぜ**やるのかを理解しているか |
| 受け入れ条件（`AC-1`, `AC-2`, …） | **ちょうどこれらが成り立てば満足か、他に必要なものはないか。** ここにないものはチェックされません |
| 変更するファイル／変更しないファイル | 触るべきでないものに手を出していないか |
| 対象外 | 必要なことが対象外にされていないか |
| 更新するドキュメント | 正しいドキュメントが挙がっているか |

良い受け入れ条件は機械的に確かめられます。「より安全にする」ではなく、「ファイルが存在するとき、終了コード 1 で終了し、標準エラーにその旨を出す」のように書かれているべきです。

**直してほしいときは**、Issue にコメントで書き、もう一度 `make spec ISSUE=12` を実行します。
フィードバックを反映した指示書の**全文**が改めて投稿され、有効なのは最新の 1 つだけです。
古い指示書を編集する必要はありません。また、あなたのコメントがそのまま仕様になるわけではありません。
新しい指示書に取り込まれて初めて仕様になります。

### 手順 4: `make impl` を実行する

```sh
make impl ISSUE=12
```

しばらく（数十分かかることもよくあります）動き続け、各ステップを Issue に投稿します。見張っている必要はありません。
終わり方は 2 通りです。

- **PR が作られる** ― 手順 5 へ
- **止まる** ― 4 章を参照

### 手順 5: PR をレビューして判断する

AI がマージすることはありません。PR 本文は人が読むために書かれていて、次を含みます。

| セクション | 何のためにあるか |
|---|---|
| 変更内容／理由 | 何を変えたか、どんな問題を解決するか |
| 各受け入れ条件の満たし方 | 各 `AC-n` をどのテストや確認で証明したか |
| レビューで指摘されたが対応していない点 | AI が対応しなかった提案（`non-blocking`）。目を通してください |
| 残存リスク | **推論だけで**通った条件（`verified:inference`）や、誰も確認していないリスク項目（`unchecked`）。**マージ前にまずここを見てください** |

PR には `CODE_REVIEW` コメントも付きます。受け入れ条件が扱っていないバグ（境界条件、握りつぶされたエラー、セキュリティ）を探す
もう一つの目です。何かを止める力はなく、指摘が重要かどうかは人が決めます。

もっと厳しいレビューがほしければ `make pr-review ISSUE=12` を実行します。PR に**反対の立場から**論じます。
目的は本当に達成されているか、テストは本当に壊れたことを検出できるか（わざと 1 行壊して確かめます）、以前動いていたものが動かなくなっていないか。
他のステップより費用がかかるので、既定では実行されません。

受け入れ条件の外でレビューが見つけた問題は、この Issue で何度もやり直すより、**新しい Issue** にするのがおすすめです。

## 3. Issue に何が投稿されるか

各コメントの先頭には、種類を表す見えないタグ（`<!-- AI-TAG: … -->`）が付いています。出てくる順に:

| タグ | 書き手 | 内容 | 人の対応は必要？ |
|---|---|---|---|
| `QUESTION` | spec | 推奨案付きの質問 | **必要** ― 回答して `make spec` を再実行 |
| `INSTRUCTION` | spec | 受け入れ条件付きの指示書 | **必要** ― 読んで、直すならコメントして `make spec` を再実行、よければ `make impl` へ |
| `PLAN` | impl | どう実装し、各条件をどうテストするかの計画 | 不要 |
| `PLAN_REVIEW` | impl | 計画がすべての条件を押さえているかの判定 | 不要 |
| `IMPLEMENTATION_DONE` | impl | 実装の報告 | 不要 |
| `CRITIC_REVIEW` | impl | 結果がすべての条件を満たしているかの判定 | 不要 |
| `FIX` | impl | 差し戻し後に直した内容 | 不要 |
| `RESIDUAL_RISK` | impl | 受け入れ条件の外に残るリスク | マージ前に読む |
| `CODE_REVIEW` | （PR 上） | 受け入れ条件の外のコードレビュー | マージ前に読む |
| `DEVILS_ADVOCATE` | （PR 上、`make pr-review` のときだけ） | PR への反論 | 実行したなら読む |

計画と実装はそれぞれ最大 3 回まで差し戻され、直されます。`PLAN_REVIEW` / `CRITIC_REVIEW` が何度も出てくるのはそのためで、
フローが正しく動いている証拠です。問題ではありません。

## 4. 止まったとき

止まり方は 2 通りあります。どちらでも作業は失われません。作業ツリーのコードも、Issue のコメントもすべて残ります。

### 「人の判断待ち」― 人が何かを決める必要がある

エラーではありません（コマンドの終了コードも 0 です）。よくあるケース:

| 見えるもの | 意味 | すること |
|---|---|---|
| Issue に質問 | 仕様が決まっていない | 回答して `make spec` を再実行 |
| 指示書 | 確認待ち | 読む（手順 3） |
| 「… was not approved after 3 rounds」 | AI が同じ条件で落ち続けた。**ほとんどの場合、受け入れ条件があいまい** | 指示書を直し（コメントして `make spec` を再実行）、もう一度 `make impl` |
| `NEEDS_HUMAN` | 条件同士が矛盾している、または誤った前提に立っていて、いくら直しても通らない | 最新の判定コメントにある選択肢を読み、`make spec` で指示書を直してから再開（下記） |

### 「中断」― 予期しないことが起きた

メッセージに、何が起きたかと**どのコマンドで再開するか**が書かれています。その通りにしてください。よくあるもの:

| メッセージ | すること |
|---|---|
| `Issue #n has no instruction document` | 先に `make spec` を実行 |
| `… modified tooling files` | 誰か（AI か人）がフロー自身のファイルを編集した。git で元に戻して再実行。**フェーズ実行中は `ai-flow/` や `.ai-flow/` を編集しないでください** |
| `… left files that fail the formatting check` | 示されたフォーマッタを実行してから `make review` |
| `No difference from origin/…` | AI がコミットしなかった。`make review` を実行 |

全一覧は [setup.md §8](setup.md#8-reading-why-it-stopped) にあります。

### 再開のしかた

| 止まった場所 | 実行するコマンド |
|---|---|
| 指示書が固まる前 | `make spec ISSUE=n` |
| 計画の段階 | `make impl ISSUE=n` |
| 実装の後（手で直した場合も） | `make review ISSUE=n` |
| レビューは通ったが、push か PR 作成だけ失敗した | `make create-pr ISSUE=n` |
| PR はあるが、コードレビューが投稿されなかった | `make code-review ISSUE=n` |

止まった後に手でコードを直した場合は、コミットせずに作業ツリーに残したまま `make review` を実行してください。AI はそこから続けます。

## 5. コツ

- **小さく始める。** 最初の Issue は 1 ファイルの修正くらいがちょうどよいです。`make spec` が指示書までたどり着くか、
  計画が 1〜2 回で承認されるかを見てください
- **止まる主な原因は、あいまいな受け入れ条件です。** 「見た目が良くなった」でしか判断できない条件は、コマンドで確かめられる形に書き直します
- **1 つの Issue に目的は 1 つ。** 目的が 2 つあると、互いに引っ張り合う条件ができてしまいます
- **質問への回答は短くてよい。** 「推奨どおりで。ただし 2 番は…」で十分です
- **通知があると便利です。** フローは長時間動くので、Slack、Google Chat、または自分で用意したコマンドに通知を設定しておくと
  （[setup.md §2](setup.md#notifications)）、終わったときや人の判断が必要なときに知らせてくれます
- **費用** ― Issue ごとの費用は `ai-flow/tmp/cost-issue<N>.txt` にあり、合計は通知にも含まれます
- **出力言語** ― コメント、コミット、PR は `.ai-flow/config.mk` の `OUTPUT_LANG` で指定した言語で書かれます（日本語なら `OUTPUT_LANG = Japanese`）

## 6. よくある質問

**`make spec` を飛ばして、指示書を自分で書けますか？**
`make spec` に書かせてください。spec は投稿前にコードを確認し、受け入れ条件に書いたコマンドをすべて実行して、判定に使えることを確かめています。
やりたいことが完全に決まっているなら、それを Issue に書けば、spec は質問なしで指示書にしてくれます。

**レビューで見つからなかった問題が PR にあります。なぜですか？**
チェックは受け入れ条件しか確かめません。どの条件にも含まれない問題は、もともと見つける仕組みがありません。
これは、レビューが堂々巡りせずに終わるための代償です。PR 上で手で直すか新しい Issue にし、
その種の問題を `.ai-flow/risk-catalog.md` に加えて、次回から `RESIDUAL_RISK` が探すようにすることを検討してください。

**PR のブランチに自分で push してもいいですか？**
はい。PR ができた後は普通の PR です。

**2 つの Issue を同時に走らせられますか？**
同じ作業コピーではできません。実行は今の作業ツリーとブランチの上で行われます。別のクローンか `git worktree` を使ってください。

**「Warning: 3 disallowed tool call(s) were denied.」と出ました。失敗ですか？**
いいえ。AI は多くの場合それを回避して進みます。同じコマンドが毎回拒否されるようなら、フローの設定を管理している人に
`.ai-flow/permissions.json` での許可を相談してください。

**詳しいリファレンスはどこですか？**
[setup.md](setup.md)（英語）: 導入、設定、権限、すべての中断メッセージ、設計上の判断。
